## 核验方式（两种，交叉确认）

### 方式 A：v2 observations API（精确、可复现）

Langfuse v1 `GET /api/public/traces/{id}` 已于 2026-11-16 下线（返回 410），改用：

```
GET /api/public/v2/observations?traceId={trace_id}&limit=10
Authorization: Basic <public_key>:<secret_key>
```

按 `traceId` 精确匹配（不是按时间窗口，避免相邻记录混查），返回的 `data` 数组长度 = span 数量。三次均返回 2 条，名称和类型分别为 `router_intent`(SPAN) 和 `router_llm`(GENERATION)。

## 首次运行超时事件（11-17 21:10:25）

第 1 次运行时 SDK 报 `Failed to export spans batch due to timeout`，Trace 未落库；重跑一次后上报成功。
**根因推测**：Langfuse 云端 JP 节点偶发抖动 + OTLP 10s 超时偏紧，而非批次太大（单 CLI 只产生 2 个 span，远低于 flush_at=512）。
**临时兜底**：`cli.py` 退出前显式 `flush()` + 进程快速退出，给 SDK 最后一次同步发送机会。

## 扩展性建议（暂不实施）

如果后续 LangGraph 接入后 span 数量显著增加（多节点 + 多意图 + 多子 agent），建议在 `get_langfuse()` 里显式设置：

```python
return Langfuse(
    public_key=settings.langfuse_public_key,
    secret_key=settings.langfuse_secret_key,
    host=settings.langfuse_host,
    flush_at=10,          # 攒 10 个 span 就发，降低单批超时概率
    flush_interval=1.0,   # 每 1s 定时 flush，不等攒满
    timeout=15,           # OTLP 导出超时放宽到 15s
)
```

调小 `flush_at` / `flush_interval` 的代价是 HTTP 请求更频繁，但在 span 数量 < 100 的场景下可忽略；LangGraph 上线后建议实测压测再决定是否调。
