## 第 1 页：封面

**标题**：线上酒类售后理赔客服工单 Agent

**核心要点**：

1. 一句话完成多意图取证、赔付建议、回复与工单草稿。
2. 只出草稿，人工审核；退款、未成年人、超时效全部转人工。
3. 技术栈：LangGraph + Redis + SQLite + Streamlit + Langfuse。

**建议配图**：双端界面同屏截图。左侧顾客端对话与补证清单，右侧商家端待审工单卡片，中间用细线分隔并标注“顾客端 / 商家端”。

**口播**：这不是一个只会聊天的客服，而是一条能落工单、能审核、能回放的售后处理链路。

## 第 2 页：背景与痛点

**标题**：售后理赔为什么需要 Agent

**核心要点**：

1. 一句话常含多个诉求：破损、少件、保存咨询同时出现。
2. 人工要分别查订单、物流、批次、政策，口径不一致。
3. 大模型直接生成有越权承诺与金额幻觉风险。

**建议配图**：左侧“人工处理：4 个系统来回切换”，右侧“Agent：一条链路完成”，用箭头对比；底部放一张真实顾客话术截图。

**口播**：痛点不是“不会回答”，而是“回答之后不敢直接执行”。

## 第 3 页：需求与边界

**标题**：做什么，不做什么

**核心要点**：

1. P0：9 个工具、Judge 质检、转人工、15 条评测、Docker 交付。
2. P1：多意图、润色、Streamlit 双端、证据上传模拟，全部完成。
3. 明确不做：自动退款、修改订单状态、P2 加分项不启动。
4. 架构选型：确定性编排 vs 自由 ReAct vs Plan-and-Execute 三方对比（选确定性编排，见 architecture §3）。

**建议配图**：三列范围表（P0/P1/P2）+ 一条红色边界线标注“资金操作必须人工”。

**口播**：范围控制的本质，是把“能演示”与“能负责”分开。

## 第 4 页：LangGraph 状态机流转

**标题**：一条主链，九个节点

**核心要点**：

1. `load_session → router → fetch_evidence → check_evidence → create_draft → polish → judge`。
2. 两条旁路：知识咨询走 `knowledge_agent`，异常/合规走 `handoff_human`。
3. Judge 失败按 `failed_node` 回跳，最多 2 次；图递归上限 32。

**建议配图**：直接使用 `docs/architecture.md` 的 LangGraph 状态图，导出 PNG；把 `judge → create_draft` 的回跳边用强调色加粗。

**口播**：状态机不是画着好看，它决定了失败时回到哪一步、什么时候必须交给人。

## 第 5 页：多意图与并发取证

**标题**：一句话拆成三个任务

**核心要点**：

1. `task_outputs` 为每个子任务独立保存结果，避免互相覆盖。
2. `ThreadPoolExecutor` 并发，`max_workers=min(任务数, 4)`，按原顺序回写。
3. 单任务失败只标记该任务，其余结果保留，整体转人工。

**建议配图**：时序图。顾客一句话 → router 拆三个子任务 → 三个线程并行 → 按索引回写 → 合并回复与工单；右侧附 U09 的 State 截图。

**口播**：并发不是为了快，而是为了不让次要诉求被主诉覆盖。

## 第 6 页：记忆与长上下文

**标题**：第二轮只说“我已经上传了”

**核心要点**：

1. Redis Key `agent:ctx:{session_id}`，保存订单、证据、重试次数，TTL 1800 秒滑动续期。
2. 合并规则：本轮输入优先，历史只补空缺；证据逐项去重保序。
3. Redis 故障自动降级为进程内字典，主链不中断。

**建议配图**：两轮对话截图 + Redis Hash 结构示意图；标注“第一轮 3 项证据 → 第二轮只带 session_id → 恢复并计算 354.00 元”。

**口播**：长上下文不是把全部历史塞给模型，而是只恢复这次决策需要的槽位。

## 第 7 页：防幻觉与 Judge 重试机制

**标题**：让模型只改表达，不改事实

**核心要点**：

1. Judge 四条标准：不承诺退款、金额一致、补证清单完整、事实不矛盾。
2. 失败按 `failed_node` 局部重跑，`MAX_JUDGE_RETRY=2`，超限 `JUDGE_REJECTED` 转人工。
3. 双层防护：`RECURSION_LIMIT=32` 防死循环；polish 代码侧锁定金额、订单号、清单、承诺。

**建议配图**：左侧 Judge 裁决 JSON 截图（pass/reason/failed_node），右侧重跑流程图；底部放一张“金额 354.00 被锁定”的 polish 对比截图。

**口播**：防幻觉不能只靠提示词，要有结构化裁决、局部重跑和代码级校验三道闸。

## 第 8 页：测试与评测

**标题**：195 条测试，15/15 通过

**核心要点**：

1. 171 条 M1~M6 功能测试 + 24 条 M7 边界与展示层测试，全量 195 passed。
2. M7 新增两类测试：UI 展示层边界 14 条（SQLite 路径错/锁/不存在三类分流）+ 工单合并视图 6 条。
3. 4 条真实 Trace（U01/U06/U09/U14），其余 11 条如实标注离线 Mock。

**建议配图**：pytest 通过截图 + 评测分布表 + Langfuse Trace 列表截图；用绿色勾标 15/15，用灰色标“未采集”的四项指标。

**口播**：通过率不是重点，重点是每个数字都能指回一条测试或一条 Trace。

## 第 9 页：业务展示（354.00 元理赔链路）

**标题**：从“酒漏了”到 354.00 元赔付建议

**核心要点**：

1. 第一幕缺证：`supplement_evidence`，金额 0，输出四项补证清单。
2. 第二幕补齐：证据 `complete=true`，1180 × 30% = 354.00 元，保价 1200 未触发封顶。
3. 商家端审核通过，旧草稿自动 `superseded`，只保留最新待审单。

**建议配图**：三张连续截图：顾客补证清单 → 赔付回复（354.00 元）→ 商家端待审工单；底部用一条时间线标注 0s / 8s / 审核。

**口播**：这一页现场配合系统操作，PPT 只保留三个关键状态，避免遮挡界面。

## 第 10 页：安全边界与异常兜底

**标题**：恶意输入也不崩

**核心要点**：

1. 无关文本 → `UNSUPPORTED_ISSUE_TYPE`；非法订单号 → `NOT_FOUND`，均转人工且不生成草稿。
2. 3000 字超长文本、SQL 注入字符均正常返回，不出现 `INTERNAL` 或 500。
3. 重复提交防连点：写入新草稿前旧 `draft` 置为 `superseded`。
4. M7 修复：SQLite 路径漂移问题——根因 CWD 漂移，修复锚定 PROJECT_ROOT（`_db_path()` 向上两级）。

**建议配图**：四行边界测试结果表 + 一张商家端只有一条待审单的截图；用红色标注“转人工”，绿色标注“系统正常返回”。

**口播**：演示现场最怕的不是答错，而是崩溃；这四条测试就是演示防线。

## 第 11 页：工程化与方案对比

**标题**：能一键启动，也能说清取舍

**核心要点**：

1. Docker Compose：Redis healthcheck 通过后启动 App，数据卷持久化；演示策略为彩排 `--build` 一次、现场仅 `up -d` 秒级启动。
2. 政策检索选择关键词加权降级：Windows 缺 C++ 编译环境，Chroma 暂缓。
3. 取舍代价：无语义泛化；收益：零额外依赖、可解释、可复现，接口保留可平滑切换。

**建议配图**：左侧 Compose 启动成功截图（Redis healthy + App started），右侧 Chroma 与关键词加权对比表。

**口播**：降级方案不是“凑合”，而是在交付约束下做出的明确取舍，并且把边界写进了报告。

## 第 12 页：总结与展望

**标题**：一条可负责的售后链路

**核心要点**：

1. 已完成：9 个工具、9 个节点、双端工作台、195 条测试（171 功能 + 24 M7 边界与展示层）、15/15 评测。
2. 三条原则：先闭环再增强、把不确定性关进笼子、用证据代替“应该可以”。
3. 下一步：向量检索、真实指标埋点、11 条 Mock 用例真实化、接入企业工单。

**建议配图**：项目能力全景图（工具层 / 编排层 / 记忆层 / 双端 / 观测）；右下角放二维码或仓库地址占位。

**口播**：系统的价值不在于替人做决定，而在于把决定所需的事实、草稿和证据准备好。
